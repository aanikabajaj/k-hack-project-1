# Fixes — August 15, 2026

Three gaps found while auditing the member/booking side against the original repo (see
[`changelog-2026-08-14.md`](changelog-2026-08-14.md) and the
[refactor audit](https://claude.ai/code/artifact/64725c89-fa30-46b5-ae4b-ce7b1a367362)),
none of which existed in the original app either — all three are things the refactor's own
restructuring made visible, not regressions from it. No public tRPC signatures, inputs, or
the schema changed.

## 1. `/waitlist` could show a stale list after joining one from `/schedule`

**File:** [`src/app/schedule/page.tsx`](../src/app/schedule/page.tsx)

Booking a full class from `/schedule` lands it as `"waitlisted"` and invalidated
`bookings.mine` and `classes.list` — but not `bookings.waitlisted`, which is the query
`/waitlist` actually reads. `/waitlist`'s own cancel handler already invalidated all three;
`/schedule`'s book handler was missing the third one. Someone with both pages open, or who
joined a waitlist and immediately checked `/waitlist`, could see a list missing the entry
they just joined until the query's 5-second `staleTime` passed on its own.

**Fixed:** added `await utils.bookings.waitlisted.invalidate();` to `book`'s `onSuccess`,
matching the pattern `/waitlist` already used.

## 2. Buying a plan while one was active created a second membership row

**File:** [`src/server/routers/plans.ts`](../src/server/routers/plans.ts)

`plans.subscribe` always inserted a new `memberships` row, with no check for an existing
active one. Two `status: "active"` rows for the same member meant every place that looks up
"the" active membership (`activeMembershipFor` in `booking-rules.ts`, `members.profile`)
picked whichever had the later `endDate` — the older row's remaining credits became
silently unreachable, even though the member had paid for them.

**Fixed:** `subscribe` now looks up an existing active membership first
(reusing `activeMembershipFor`, the same helper `bookings`/`reschedules` already share).
If one exists, it's topped up in place instead of a second row being created: credits add,
and the end date extends from the *existing* membership's end date rather than resetting
from today, so buying early doesn't cost the days already paid for. First-time or lapsed
members are unaffected — no existing active membership means a fresh row, same as before.

Not applicable to `member-booking-refactor/` — `plans.ts` isn't part of that folder's file
set even though the member side owns it (see that folder's own fixes doc).

## 3. `book`, `cancel`, and `reschedule` weren't atomic

**Files:** [`src/db/index.ts`](../src/db/index.ts),
[`src/server/routers/booking-rules.ts`](../src/server/routers/booking-rules.ts),
[`src/server/routers/bookings/member.ts`](../src/server/routers/bookings/member.ts),
[`src/server/routers/reschedules.ts`](../src/server/routers/reschedules.ts),
[`src/server/routers/plans.ts`](../src/server/routers/plans.ts)

Each of these mutations was a sequence of separate reads and writes against `ctx.db`, not
one transaction: `book` checked capacity, then inserted, in two round trips; `cancel`
updated the booking, then refunded, then promoted the next waitlisted member, in three;
`reschedule` did all of that plus an insert and a second update. Nothing wrapped the
check-then-write pairs, so two requests racing each other (two members going for a class's
last open spot at the same moment, for example) could both read "not full" before either
had written anything, and both land as `"booked"` past capacity.

**Fixed:** added a `DbOrTx` type in `db/index.ts` - `typeof db | ` the transaction-callback
parameter type, derived generically rather than importing a libsql-specific type name - so
the existing `booking-rules.ts` helpers (`activeMembershipFor`, `isClassFull`,
`refundIfEligible`, `promoteNextWaitlisted`) and `reschedules.ts`'s `checkReschedule` accept
either `db` or a `tx` unchanged. `book`, `cancel`, `reschedule`, and `subscribe` now each
run their full body inside `ctx.db.transaction(async (tx) => ...)`. SQLite serializes
writers around a transaction the same way it would a single statement, so the check and the
write it gates can no longer be split by a concurrent request. Read-only queries
(`bookings.mine`, `reschedules.history`, `validateReschedule`, `plans.list`) were left as
plain `ctx.db` calls - nothing to make atomic there.

### Verified

Typechecked clean (`tsc --noEmit`, zero errors) and exercised end-to-end against a running
`pnpm dev`, logged in as a seeded member:

- `bookings.book` on a class that had already started correctly rejected inside the
  transaction, and rolled back cleanly - credits were unchanged after the rejection.
- `bookings.book` on an open class succeeded, deducted one credit, and a repeat call
  correctly hit the duplicate-booking `CONFLICT`.
- `bookings.cancel` on that booking refunded the credit (well outside the 12-hour window).
- `plans.subscribe` on a plan while one was already active topped up the same membership
  row: credits went from 5 to 15 (+10 from the new plan), end date pushed from
  `2026-11-12` to `2027-02-10` (+90 days) - same membership `id`, not a second row.
- `reschedules.reschedule` moved a booking to a same-name class in a later slot and
  recorded it in reschedule history correctly.

No server-side exceptions in any of the above; all three affected pages
(`/schedule`, `/waitlist`, `/plans`) render without errors.
